# ADR-0002 — Campaign Event Log как канонический источник состояния

**Дата:** 2026-07-29
**Автор:** Lead Software Architect
**Статус:** Accepted for synthetic development only

## Контекст

`ADR-0001` и migration `001_campaign_current_state_projection` реализовали
`leasemind_app.campaign_current_state_projection` как единственное
техническое хранилище состояния Campaign, с прямой записью через synthetic
seed. `LeaseMind_AI_MANAGER_ARCHITECTURE_v1.0.md` (Approved, v1.0, раздел 5.1)
определяет состояние Campaign как производное от двух источников:

- **Immutable Event Log** — неизменяемая последовательность событий;
- **Current State Projection** — актуальное расчетное состояние.

До этого решения Event Log не существовал технически: projection была
единственным хранилищем, что противоречит разделу 5.1 и не позволяет
восстановить состояние Campaign после ошибки, как того требует §5.1
("восстановить ход Campaign... пересчитать состояние после исправления
ошибки"). Раздел 20 (MVP AI Manager, пункт 2) прямо включает "Event Log и
Current State Projection" в первую реализацию.

Раздел 2 (Архитектурные границы, пункт 6) требует: "AI-агенты не изменяют
состояние Campaign напрямую". Раздел 7 требует идентификатор идемпотентности
для каждой задачи. Раздел 17 требует безопасный повтор только идемпотентных
операций. Ничего из этого не реализует бизнес-переходы статусов — переходы
между статусами Campaign целиком остаются вне этого документа (см. §5.3:
"Статус не управляет процессом как жесткий линейный сценарий").

## Решение

Для **синтетической DEVELOPMENT-разработки** вводится:

1. **Event Log — источник истины.** `leasemind_app.campaign_event_log`
   становится каноническим техническим источником состояния Campaign.
   `campaign_current_state_projection` (migration 001, без изменений)
   остаётся производной, пересчитываемой read-проекцией — она никогда не
   пишется напрямую, только атомарно вместе с добавлением события или через
   явную функцию восстановления (rebuild).

2. **Один технический тип события.** Определён ровно один event type:
   `campaign.status_recorded.v1`, `schema_version = 1`. Его payload содержит
   единственное поле `status` — одно из 11 утверждённых значений
   (`LeaseMind_AI_MANAGER_ARCHITECTURE_v1.0.md`, §5.3). Событие фиксирует
   технический факт "для Campaign записан статус X" и **не вводит и не
   определяет никакого нового бизнес-правила перехода между статусами** —
   когда, кем и почему статус может меняться, остаётся полностью вне этого
   ADR и вне кода, реализующего Event Log.

3. **Без HTTP write API.** Ни один HTTP endpoint не создаётся и не
   изменяется для записи событий. Единственный способ добавить событие —
   внутренняя функция приложения (`apps/api/src/db/campaignEvents.ts`),
   вызываемая только из synthetic seed и тестов. AI-агенты (когда появятся)
   не получают отдельного или более широкого доступа к записи, чем synthetic
   seed уже имеет сегодня — это согласуется с §2.6 ("AI-агенты не изменяют
   состояние Campaign напрямую") и §8.3.2 её агентского контракта.

4. **Server-owned identity, время, sequence, хэши.** Вызывающий код передаёт
   только `campaign_id`, `status` и `idempotency_key`. `event_id` (UUID v4),
   `event_sequence` (строго возрастающий per-campaign, начиная с 1),
   `occurred_at` (время БД, `clock_timestamp()`, получаемое ровно один раз на
   вызов), `command_hash` и `event_hash` всегда вычисляются и назначаются
   сервером — вызывающий код не может их подделать или предсказать заранее.

5. **Идемпотентность и hash chain.** Каждое событие хранит:
   - `idempotency_key` — уникален в пределах `campaign_id`;
   - `command_hash` — SHA-256 от запрошенной команды (`campaign_id` +
     `status`), позволяет отличить "тот же ключ + та же команда" (безопасный
     повтор, возвращается исходное событие без дубля) от "тот же ключ +
     другая команда" (отклоняется, ничего не пишется);
   - `previous_event_hash` — хэш предыдущего события того же potока
     (`repeat('0', 64)` для первого события) и `event_hash` — доменно
     разделённый SHA-256 (`LEASEMIND_CAMPAIGN_EVENT_V1`) от собственных полей
     события и `previous_event_hash`. Вместе они образуют проверяемую цепочку
     на поток одной Campaign.

   Append одной Campaign сериализуется через `SELECT ... FOR UPDATE` на
   строку `leasemind_app.campaign_stream_head` (внутренний курсор, не
   бизнес-сущность), что гарантирует строго последовательные `event_sequence`
   при параллельных вызовах без потери и без дублирования номеров.

6. **Immutable по конструкции.** `campaign_event_log` не допускает `UPDATE`
   и `DELETE` — оба безусловно отклоняются триггером на уровне таблицы,
   независимо от роли, выполняющей запрос.

7. **Rebuild — читает Event Log, не изменяет его.** Добавлены функции
   восстановления одной или всех Campaign projection из Event Log. Rebuild
   всегда воспроизводит `campaign_current_state_projection` в состоянии,
   соответствующем последнему событию потока, и никогда не пишет и не
   удаляет ничего в `campaign_event_log`.

8. **Synthetic-only.** Payload события ограничен единственным полем `status`;
   платежи, Matching, Reveal, Introduction Record, ПДн, контакты и адреса
   технически невозможно поместить в это событие (constraint запрещает любые
   дополнительные ключи и вложенные структуры). Реализация остаётся в рамках
   `ADR-0001` — только synthetic data, только локальный disposable PostgreSQL.

## Явно НЕ входит в это решение

- Это **не** матрица переходов статусов и не бизнес-правило "какой статус
  может следовать за каким". Событие `campaign.status_recorded.v1` технически
  принимает любое из 11 утверждённых значений без проверки предыдущего
  статуса — сама допустимость перехода не проектируется и не реализуется
  здесь.
- Это **не** предоставление AI-агентам права писать события. Contract из §8
  и ограничение §2.6 не меняются; запись событий остаётся доступной только
  внутреннему коду приложения (seed/tests), без HTTP-поверхности.
- Это **не** реализация Decision Engine, Strategy Manager, Task Planner или
  любого другого компонента AI Manager из разделов 3–20 — они спроектированы
  в архитектуре, но не реализуются этим ADR.
- Это **не** изменение утверждённых 11 статусов, их значений или порядка
  (§5.3) и не изменение migration `001_campaign_current_state_projection`.
- Это не решение о production-развёртывании, ORM или новых внешних
  зависимостях — реализация использует существующий стек (`ADR-0001`) и
  встроенный `node:crypto`, без новых production-зависимостей и без
  расширений PostgreSQL.

## Последствия

- `campaign_current_state_projection` может быть полностью пересчитана из
  `campaign_event_log` в любой момент (rebuild), что удовлетворяет §5.1
  ("восстановить состояние после исправления ошибки").
- Любое будущее подключение AI Manager (Decision Engine, Autonomy Policy
  Gate и т.д., §12) к записи состояния Campaign обязано проходить через тот
  же единственный append-путь и тот же формат события — расширение на новые
  event types или изменение формы payload требует новой ревизии этого ADR.
- Появление реальной матрицы переходов статусов, авторизации записи для
  AI-агентов или HTTP write API остаётся отдельным, отдельно утверждаемым
  решением DEVELOPMENT/Founder и не разблокируется автоматически этим ADR.
